# AI合同会社 (AMONE) 共通連携: 最小設計 (sandbox)

COLLAB-005 / COLLAB-006 (v1.3) に基づく。振り分けの部品 (PR #14) と、GitHub上の受付の仕組み。
合成データのみ。本番・Secrets・課金・設定には触れない。

## 役割 (v1.3)
- よしひろ: 最終判断。モネ: 開発・テスト・PR・窓口。Codex: PRの独立レビュー。
- アムChat: 調査・設計・相談・頼まれたレビュー。Work: 画面操作が必須のときだけ。
- GitHub Actions: 自動の検証と、承認済みの反映。
- Chatを GitHub の出来事から人手なしで起こす方法は **未実証** (`UNSUPPORTED` のまま)。

## 構成
- **登録台帳** `collab/registry.example.json`: repo、窓口、許可レーン、許可操作、承認が要る操作 (`approvalRequired`)、画面操作が必須の操作 (`guiOperations`)、通知先、優先度。新しいプロジェクトは1件足すだけ。
- **ルーター** `src/router.js` (純粋関数、GitHubには触らない)
  - `parseRequest`: `[MONE-REQUEST] id=<ID> lane=<chat|work|codex|mone> op=<操作> status=open|cancel sha=<SHA>` を読む。既存の書式 `[MONE-ASK]` / `[AMU-ANSWER]` / `[MONE-REQUEST]` / `[AMU-RESULT]` を維持し、新しいID体系は作らない。
  - `decide`: `route / reject / cancel / skip-duplicate / skip-cancelled / needs-approval` を返す。
  - `guardSideEffect`: コメント投稿・書き込み・反映の **直前** に、依頼が `open` か・振り分け済みか・取消・投稿済み・中身の差し替え (lane/op/SHA/flags)・あとから足された危険な操作やflag・SHAのずれ・PRなのにSHAがない・PRかどうかが不明、を確かめて止める。PRかどうかは、呼び出し側がGitHubの確かな情報から必ず渡す (渡さなければ止まる)。
- **状態**: 依頼の鍵は `repo#Issue/PR番号#依頼ID`。Issue/PR番号は正の整数、依頼IDは英数字と `. _ -` だけ (区切りの `#` が混ざらない)。正本はGitHub。

## 守ること (このPRのルーター関数の中での約束)
- 取消が最優先。振り分け済みの依頼や、元のコメントを編集しての取消も効く。取消済みの依頼は動かさない。
- 同じコメントID・同じ依頼は、渡された台帳の上では二度振り分けない。同じコメントの依頼IDを書き換えても、2つ目の依頼にはならず拒否する。
- 知らない `status`、`op` のない依頼、不正な番号やIDは拒否する (安全側)。
- 承認が要るかは **登録台帳と操作の中身** で決める。コメントに「承認済み」と書いてあっても承認とみなさない。課金・本番・反映・Secrets・権限・削除・公開は、台帳の書き漏れがあっても必ず止めて聞く。
- Workレーンは、台帳の `guiOperations` に書いた操作だけ。
- 止めたChatGPTのGitHub連携の予定タスクは、アカウント解除の後も、よしひろさんがはっきり指示するまで再開しない。
- 公開されるログに、秘密・非公開のURL/ID・個人情報・環境変数・APIの応答を出さない。

## GitHubの使い方 (アカウント停止の後の決まり。COLLAB-006 の暫定件数を置きかえ)
- PR・コメントの1日の件数に、独自の上限はつけない。
- 失敗したら、そこで止まる。同じことを自動でやり直さない。やり直すのは、原因を直してから1回だけ。
- 失敗が2回続いたら、その仕組みを止めて、よしひろさんに報告する (止めるのはモネかよしひろさん)。
- 失敗のお知らせは1件にまとめる。続けて何件も書き込まない。
- GitHubに止められたら、別のアカウントを作らず、止まって報告する。

## 受付の仕組み (`.github/workflows/collab-intake.yml`)
持ち主が `[MONE-REQUEST] ...` で始まるコメントを書く (または編集する) と、GitHub Actions が動いて、担当を知らせるコメントを **1件だけ** 書く。

1. 動くのは、書き手が持ち主で、先頭が `[MONE-REQUEST]` のコメントだけ。持ち主かどうかは、GitHubの印 (`author_association == OWNER`) と、リポジトリの持ち主のアカウントIDの両方で確かめる。ほかの人のコメントでは何も起きない。
2. `scripts/intake.js` が、最新のコメントと、そのIssue/PRの全コメントを読む。次のどれかなら、何も書かずに止まる (読んだデータが信用できないときは、部分的な記録で判断しない)。
   - コメントが1000件以上ある / 途中のページが読めない (404 など) / ページの中身が一覧でない
   - 一覧の中に、形のおかしいコメントが1件でもある (番号・本文・書き手が欠けている)
   - PRの先頭のコード番号が分からない、または正しい形 (英数字40文字) でない
   - ボットの記録コメントが、受付の仕組みが書いたとおりの文と1文字でも違う。記録コメントの文は、中の記録 (印) から毎回まったく同じに作られる。読むときは、印から文を作り直して、実際のコメントと比べる (改行の `\r\n` と `\n` の違いだけは同じとみなす)。印が読めない・印が2つある・印が消えたのに `[AMONE-` で始まる・状態が `routed`/`cancelled` 以外・知らない項目がある・鍵が別の Issue/PR のもの、も同じく止まる。
   - (ボットのコメントでも、印がなく `[AMONE-` で始まらないものは、ほかの仕組みのコメントとして無視する)
3. 状態は別の保存場所を持たない。ボット (`github-actions[bot]`) が書いたコメントの中の印 (`<!-- amone:v1 ... -->`) から毎回組み立て直す。ほかの人が同じ印を書いても信じない。
4. `src/intake.js` の `plan` が `decide` を呼び、書く文を決める。
   - 振り分け: `[AMONE-ROUTED] request=<ID> lane=<担当> op=<操作> comments=<元コメント番号> sha=<SHA か -> flags=<flags か ->`
   - 取消: `[AMONE-CANCELLED] request=<ID> lane=… op=… comments=… sha=… flags=…`
   - 拒否・承認待ち: `[AMONE-STOPPED] reason=<理由> comment=<元コメント番号>` (同じコメント・同じ理由では1回だけ)
   - 中の記録 (印) の項目は、全部この1行目にも出す。中だけを書き換えると見える文と食い違うので、必ず止まる。
   - 重複・取消済み・他人の書き込み: 何も書かない
   - 持ち主の取消コメントが同じIssue/PRにあれば、まだ処理されていなくても振り分けない
5. PRでは `sha=` が必須で、今のPRの先頭と合わなければ止める。
6. 書く直前に、全部をもう一度読み直して、もう一度判断する (元のコメントの本文と書き手、取消を含むほかの全コメント、すでに書かれた結果、PRの先頭)。次のどれかが1回目と違えば、書かずに終わる: 書く予定の文、元のコメントの本文 (2行目以降も含む)・更新時刻・書き手、PRの先頭。
7. 失敗したら、やり直さずにそのまま失敗で終わる。ログに出すのは決まった記号 (`E_API_POST_403` など) だけで、コメントの本文・鍵・URL・APIの応答は出さない。確かめていない文字 (IDなど) は、コメントに写さない。

### 保証できること・できないこと
- できること: 1回の実行で書くのは多くても1件。読み直しの時点で取消・結果・新しいpush・依頼の編集があれば書かない。同じIssue/PRの実行は1つずつ順番に動く。持ち主の取消コメントがあれば、まだ処理されていなくても新しく振り分けない。
- **できないこと**: 読み直してから書くまでのごく短い間に起きた変化は、防げない。GitHubのコメントには「1回だけ書く」ことを保証する機能がないため。書いた直後に通信が切れた場合も、やり直さない (次の実行は、書かれた印を見て重複を避ける)。
- 取消の受付コメント (`[AMONE-CANCELLED]`) が必ず書かれるとは限らない。実行が待ちのうちに捨てられると (下の「分かっている限界」)、取消コメントは処理されない。ただしその場合も、取消された依頼が新しく振り分けられることはない。
- ボットの記録コメントを消すと、記録も消える。消さないこと。書き換えて壊した場合は、その Issue/PR の受付は止まる (二重には受け付けない)。直すには、壊したコメントを元に戻す。
- 元の依頼コメントの番号が、記録のとおりに本当にその依頼のものかは、照らし合わせない。照らし合わせると、持ち主が自分の依頼を書き直しただけで、その Issue/PR の受付がずっと止まってしまうため。中だけの書き換えは上の「1行目にも出す」で見つかり、元の依頼を別のIDに書き直した場合は、記録の番号から「その依頼はもう使われている」と分かって断る。
- 登録台帳の操作の名前は、英数字と `. _ -` だけにする (記録に写すため)。違えば、その台帳は使わない。
- 記録コメントの「見える文」と「印」の両方を、つじつまが合うように書き換えた場合 (たとえば A1 の記録を、文も印もそろえて B1 に変える) は、正しい記録と区別できない。ボットのコメントを書き換えられるのは持ち主だけなので、持ち主がわざと書き換えることは想定しない。

### 失敗が続いたとき (手で止める。自動では止まらない)
- この仕組みは、失敗の回数を数えない。2回続けて失敗しても、**自動では止まらない**。人が止めるまで、次のコメントでまた動く。
- 失敗に気づく方法: GitHubの通知設定によっては「Run failed」のメールが届く。届かないこともあるので、依頼を書いたのに受付コメントが付かないときは、Actions の画面で `collab-intake` の実行履歴を見る。
- 止める人: モネかよしひろさん。アムは止めずに、よしひろさんとモネに報告する。
- 止め方: Actions の画面で `collab-intake` を「Disable workflow」にする。止めたら、止めた人が Issue #13 に1件だけ書く。止めたことを確かめられないときは、「止まっていない」として扱う。
- 戻し方: 原因を直してから「Enable workflow」に戻し、練習用のIssueで1回だけ試す。
- 失敗のお知らせは、この仕組み自身は書かない (失敗したときにまた書き込むと、失敗が続くおそれがあるため)。
- Actions にも、独自の件数の上限はない。

**この仕組みがしないこと**: アムのChatやWorkを直接起こすこと。

**Workの起動 (ChatGPT側の公式機能)**: よしひろさんの ChatGPT に、出来事で動く Work の予定タスク「AMONE Work依頼受付」を保存してある (2026-11-10、有効)。
- きっかけ: このリポジトリの、ラベル `amone-work` が付いた **PR** への新しいコメント。起動したあと、投稿者が `github-actions[bot]` で、1行目が `[AMONE-ROUTED]` で始まり、同じ1行目に `lane=work` があるときだけ進む (投稿者で絞る設定はきっかけの側にないため、起動後に確かめる)。
- ラベル `amone-work` は受付の仕組みが付け外しする。
  - **付ける**: PRで Work の依頼を振り分けるとき、受付コメントを書く**前に**付ける。付けられなければ、何も書かない。付けたあと、もう一度全部を読み直し、状況が変わっていたら何も書かない。
  - **外す (この1つの決まりだけ)**: そのPRで Work に振り分けた依頼が**全部**終わったとき。終わったとは、記録が「取消」になっているか、持ち主のアカウントの `[AMU-RESULT] request=<ID>` があること。外すきっかけは、`[AMU-RESULT]` が書かれた (編集された) ときと、Work の依頼の取消コメントを書いたあと (その取消コメントが読めることを確かめてから) の2つ。
  - **失敗したときや、状況がはっきりしないときは、外さない**。ラベルが残っても、Work が起きて条件外で終わるだけ。早く外れると、Work が必要なときに起きないので、そちらを避ける。
  - 結果のコメントは、その依頼を振り分けた記録コメント**より後に**書かれたものだけを数える (GitHubのコメント番号は後のものほど大きい)。同じIDの古い結果は数えない。
  - 残ったラベルは、次に上の決まりを満たしたときに外れる。急ぐときは、よしひろさんかモネがPRの画面で外してよい。ラベルが残るのは、たとえば: 最後の取消コメントがすぐに読めなかった / ラベルを外すのに失敗した / 受付の前に取り消された。
  - **分かっている限界**: 受付コメントの書き込みが「失敗」と返ったのに、GitHubの中で遅れて保存された場合、その間に別の Work の依頼が終わると、受付コメントより先にラベルが外れ、その依頼で Work が起きないことがある。この場合、受付の実行は「失敗」として記録に残る。ラベルを付け直すだけでは Work は起きない (Work が起きるきっかけは、ラベルではなくコメントのため)。失敗を見たら、次の順に1回だけ行う:
    1. そのPRで、その依頼の `[AMU-RESULT]` がないこと (Work が動いていないこと) を確かめる。
    2. 元の依頼を取り消す (`[MONE-REQUEST] id=<元のID> status=cancel`)。
    3. 新しいIDで、同じ依頼を1回だけ出し直す。受付の仕組みがラベルを付けて受付コメントを書き、Work が起きる。
- ラベルが付いている間は、そのPRのほかのコメントでも Work が起きる (条件に合わず、何もせず終わる)。そのため、Work の依頼は、できるだけ短い間で終わらせる。
- 同じPRで Work の依頼が2つあっても、両方が終わるまでラベルは残る。ただ、Work の依頼は、なるべく1つのPRで1つずつ出す。
- やること: 元の依頼と最新の状態を確かめ、`op=` に書かれた画面操作だけを行い、`[AMU-RESULT] request=<ID>` を1回だけ書く。パスワードや認証コードが要る所では止まる。
- Issue のコメントでは動かない (公式の機能がPRだけのため)。Issue の Work 依頼と、Chat の依頼は、今までどおり「よしひろさんがアムに伝えてください」。
- Work の使用量は Codex と共有。1回の起動でどれだけ減るかは、まだ確かめていない。
- 登録台帳で Work に許可している操作は `screen-check` (画面の確認) だけ。増やすときは、Work にさせて安全な、軽い操作に限る。

**記録の文を変えるときの注意**: 受付のコメントの文は、記録から作り直して比べている。すでに記録が書かれている担当 (lane) の文を変えると、その記録が「壊れた記録」として読まれ、その Issue/PR の受付が止まる。文を変えるのは、まだ記録のない担当だけにする。

**分かっている限界**: 同じIssue/PRで3つ以上の出来事が続けて起きると、GitHubの決まりで、待っている実行は一番新しいものだけが残る。その場合、間のコメントは処理されないことがある (処理されなかった依頼は、編集し直せばもう一度受け付けられる)。

### ルーター関数だけで見たときの限界
ルーター (`decide` / `guardSideEffect`) は、渡された台帳だけで判断する純粋な関数で、それ自体は同時実行や投稿の一回きりを守らない。受付の仕組みでは、次のように補っている。
- **同時実行**: ワークフローの `concurrency` で、同じIssue/PRの実行を1つずつにしている (実装済み)。
- **投稿の一回きり**: 書く直前の読み直しで、ほかの実行の結果があれば書かない (実装済み)。ただし、読み直してから書くまでの一瞬は防げない (上の「保証できること・できないこと」)。
- **保存の競合と中断からの復旧**: 別の保存場所を持たず、毎回ボットのコメントから組み立て直す。途中で止まった実行は、何も書いていないか、1件書き終えているかのどちらか。

## 決まっていないこと (このPRでは決めない)
1. 自動Mergeを続けるか、よしひろのMerge 1タップに揃えるか。決まるまで自動Mergeは標準にしない。
2. 非公開リポジトリの無料プランで、ブランチ保護や必須チェックがどこまで効くか。効かなければ自動反映しない。
3. 本番ではない「試験用の反映先」をどこに置くか。
4. GitHub Supportの案内に基づく、自動化の安全な条件。
5. Chatを即時に起こす公式の方法。
6. MagicPath・PostHog は任意の補助。このPRの必須にはしない。

## 次の段階
- Merge の後、練習用のIssueで「依頼 → 受付コメント」「編集で取消 → 取消コメント」「同じ依頼をもう一度 → 何も書かれない」を1回ずつ確かめる。
- ほかのプロジェクトで使うときは、そのリポジトリに登録台帳と受付の仕組みを置く (よしひろさんの承認の後)。
